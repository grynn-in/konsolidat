# Semantic Layer & Read Paths (Cube.js vs Frappe-direct)

Konsolidat exposes the ClickHouse gold layer to clients through **two
deliberate read paths**. This note records why both exist and the rule that
keeps them consistent.

## The two paths

| Path | Used by | Role |
|---|---|---|
| **Cube.js SQL API** | Excel ODBC, BI tools, high-concurrency dashboards | **Core semantic layer.** Caching, pre-aggregations and a stable metric contract let reads scale to the target **50–500 users** without every client hitting raw ClickHouse. |
| **Frappe direct query** (`konsol.api.epm_*` → `konsol/clickhouse.py`) | The `=EPM()` worksheet formulas and budget write-back | **Source of truth** for formula semantics, auth, and write-back. Runs inside the Frappe app so it shares the permission model (see entity-level authorization in `konsol`). |

Cube is **not optional** — it is the layer that makes the read side scale. The
Frappe path is not a replacement for it; the two serve different consumers.

## Why not collapse to one path

- Routing every `=EPM()` call through Cube would put Cube on the critical path
  for auth and write-back, which live in Frappe.
- Routing every dashboard/ODBC read through Frappe would not scale to hundreds
  of concurrent users — that is exactly what Cube's caching/pre-aggregations are
  for.

## The consistency rule

Because a measure can be defined in **both** the Cube schema and the Frappe
direct SQL, they must agree. The guard rails:

1. **Single upstream.** Both paths read the same dbt **gold** models. Measure
   logic lives in dbt, not duplicated in either client path.
2. **Generated Cube schema.** Cube schemas are generated by
   `scripts/generate_cube_schemas.py` from the gold models — do not hand-edit
   them so they drift from the warehouse.
3. **Parity expectation.** A measure surfaced in both paths must return the same
   number for the same coordinates. When adding a measure to one path, add it to
   the other (or consciously decide it is path-specific and document why).

## Quick decision guide

- Building a **formula / write-back** feature → Frappe `konsol.api`.
- Building a **dashboard / ODBC / high-concurrency read** → Cube SQL API.
- Adding a **metric** → define it in dbt gold; expose through whichever paths
  need it, keeping definitions aligned.
